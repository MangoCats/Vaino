# SPEC022: Syncing a Flag's Fate, and a Console GUI Over It

**Design Specification — Tier 2**

Split out of [SPEC006 §9](SPEC006-data-flow-and-portability.md#9-syncing-an-applied-edit-to-a-remote-installation) once it grew past that document's own 300-line limit `[GOV-DOC-010]` — §9's own three-way merge (`export_changes.py`/`apply_changes.py`) is the mechanism this closes a loop around, and stays there; everything below is that loop, and the console GUI built over it.

> **Related:** [SPEC006 §9](SPEC006-data-flow-and-portability.md#9-syncing-an-applied-edit-to-a-remote-installation) — the three-way merge this depends on · `tools/export_flags.py`, `tools/import_flags.py`, `tools/apply_changes.py`, `tools/jobs.py`, `tools/console.py`, `tools/console_web/flags.html`

## 1. Syncing a flag's fate to a remote installation

Designed 2026-08-27, against `[REQ-LIB-195]`. [SPEC006 §9] answers "a correction made on the desktop reaches an appliance that already holds the music." It assumes the desktop already knows *which* passage or recording to correct. `listener_flags` (`[REQ-VIS-265]`) is how a listener names one from vainopi's own chair, mid-play, on a machine with no Sampo to act on it — this is the leg that gets the name off the appliance, onto the desktop where Sampo can act on it, and the resulting correction back, closing a loop §9 alone cannot: nothing in it starts from "here is what to look at" rather than "here is what changed."

**`[SPEC-DF-107]` The portable form of a flag is the same shape §9 already uses for a decision — an anchor, not a local key.** `listener_flags` keys a recording-kind flag by its mbid (already portable) and a passage-kind flag by a local `passage_id` (not portable at all — the same gap `[SPEC-DF-103]` closed for `boundary_review`). A flag has no baseline or target to compare, so it borrows only the anchor half of §9's shape, not the three-way merge: `{"subject_kind": "recording", "anchor": {"recording_mbid": "..."}}` or `{"subject_kind": "passage", "anchor": {"audio_md5": "...", "passage_kind": "...", "start_ms": 0, "end_ms": 0}}`, plus `flagged_at` and `origin`. `tools/apply_changes.py`'s existing `resolve_passage()` — already exactly "anchor in, local `passage_id` out" — resolves the second case unchanged; nothing new was needed for it.

**`[SPEC-DF-108]` vainopi has no Python, and nothing here asks it to grow one.** The appliance ships `sqlite3` (the CLI, for `[PI5-LIB-010]`-style maintenance) but not `python3` `[VainoPi/setup-vainopi.sh]` — deliberately: an appliance that never runs Sampo has no reason to carry a runtime `[REQ-LIB-175]`'s own `sampo-support` gate already established for the player itself. Both new tools below therefore run on the *desktop*, against a **copy** of vainopi's database (`scp pi@vainopi:/srv/library/vaino.db .`, the plain version) — the same posture §9's own transport already uses, and the copy needed here is no extra cost: it is the same copy the push-back leg below needs anyway, pulled fresh immediately before it is read.

**`[SPEC-DF-109]` Two tools, the same rehearse-by-default shape as every tool here:**

```
scp pi@vainopi:/srv/library/vaino.db /tmp/vainopi-copy.db
python tools/export_flags.py /tmp/vainopi-copy.db -o flags.json

python tools/import_flags.py <desktop's own db> flags.json               # rehearsal
python tools/import_flags.py <desktop's own db> flags.json --commit
```

`export_flags.py` is read-only, mirrors `export_changes.py`'s envelope (`{"format_version": 1, "flags": [...]}`), and silently drops a passage-kind flag the copy itself can no longer resolve to a live passage — there is nothing to anchor it to, the same reasoning `[SPEC-DF-102]` already applies to a review row missing its baseline. `import_flags.py` resolves each anchor against the desktop's *own* library and reports, rather than silently drops, whatever does not match — libraries that "overlap" are not identical by definition, and a flag Sampo's own `/flags` page could not resolve would be exactly the blank rendering `[REQ-LIB-190]` was built to avoid. A flag already present locally (matched by the same resolved subject) is skipped, so a second pull after the first is harmless. Landing a new one stamps `origin` with vainopi's hostname (added to `listener_flags` as a nullable column, migrated the same way `[SPEC-DF-104]` added it to the three review tables) — a pulled flag reads identically to a local one everywhere except there, the same provenance discipline as `[SPEC-DF-104]`.

**`[SPEC-DF-110]` The write back to vainopi still cannot be a whole-file copy — `[PI005]`'s own precedent already says why.** vainopi's live database is not disposable: `[PI5-LIB-010]` explicitly named `[SPEC-SUI-100]`'s merge-don't-overwrite rule as the one a straight copy would otherwise have violated, spared only because that swap's own listening history was deliberately being discarded. A patch made between the two pulls above — a play, a new flag, an appliance that has kept running for days while the desktop review happened — is exactly what a second whole-file copy would erase. §9's `apply_changes.py` already never does this (`passages`, `passage_recordings`, `recording_artists`, and the review journals only); it only had no way to *run* on a target with no Python.

**`[SPEC-DF-111]` `apply_changes.py --emit-sql OUT.sql` replaces "commit through this process's own connection" with "commit through vainopi's own `sqlite3` CLI, later."** Given a **read-only** copy to compare against, it runs the identical three-way merge §9 already does — every `apply_id_review` / `apply_boundary_review` / `apply_artist_review` call unchanged — and captures the literal, fully-quoted statements SQLite actually executed (via `sqlite3.Connection.set_trace_callback`, which expands bound parameters into safe literal SQL, not the placeholder form) into a file instead of committing them, then rolls the compare copy back untouched. The result is an ordinary, idempotent SQL script — including the `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ADD COLUMN` statements `ensure_review_tables` already always ran, so a target missing the review tables entirely still gets them — applied with the one command vainopi already has:

```
scp pi@vainopi:/srv/library/vaino.db /tmp/vainopi-copy.db          # fresh -- not the Hop-1 copy
python tools/export_changes.py <desktop db> -o changes.json
python tools/apply_changes.py /tmp/vainopi-copy.db changes.json --commit --emit-sql patch.sql --clear-flags
scp patch.sql pi@vainopi:/tmp/patch.sql
ssh pi@vainopi 'systemctl stop vaino && sqlite3 /srv/library/vaino.db < /tmp/patch.sql && systemctl start vaino'
```

**`[SPEC-DF-112]` `--clear-flags` closes the loop the checkbox itself already models.** `[REQ-VIS-265]`'s flag is "please look at this," not a judgement, cleared the same way it was set: by hand, at any time. A change landing here for exactly the subject a flag named is that looking-at having happened, so `--clear-flags` deletes the plausible `listener_flags` rows for a change it successfully applies: `('passage', <the resolved local passage_id>)` always, and for an `id_review`, `('recording', ...)` under *both* the target mbid and the baseline one — a listener most often flags a misidentification while it still carries the wrong id, so the id being corrected away from is at least as likely to be what was flagged as the id it becomes. It is opt-in and additive to what `--emit-sql`/`--commit` already write, never assumed: not every applied change originated from a flag, and a change that did not still clears nothing that was never set.

**`[SPEC-DF-113]` Neither tool here needs Sampo's console to touch vainopi at all.** Every command above is exactly the text a "Pull flags…" / "Push changes…" button in Sampo could print for `open_terminal()` `[IMPL007 Stage 5]` to open, the identical shape the export page already uses for Case 1 — Sampo prepares, a person's own terminal runs. A GUI wrapper is a later convenience, not a prerequisite: every command is a plain, typeable line today.

## 2. A console GUI for §1, its measured cost, and a design to keep it fast

**Built 2026-08-29, on top of `[SPEC-DF-108..113]` exactly as specified — a "Sync with a remote" section in the console's own `/flags` page, one remembered remote per library (`user@host:/path`, in the console's own sidecar, never in `vaino.db`), and two jobs through the existing job model `[SPEC-SUI-080]`:** `remote-pull` runs `remote_flags.py` → `import_flags.py --commit` (originally `scp` → `export_flags.py` → `import_flags.py --commit`; replaced by `[SPEC-DF-119]` the same day), reporting matched/already/unmatched exactly as `[SPEC-DF-109]` already computes it. `remote-push` runs `scp` → `export_changes.py` → `apply_changes.py --commit --emit-sql --clear-flags` → `scp` the patch → `ssh ... systemctl stop vaino && sqlite3 ... && systemctl start vaino`, batched and triggered only on request — never per edit, since the last stage briefly stops whatever is playing in the house. Both tools gained a `--json` final-line summary (the same `parse_json_tail` convention `[IMPL-SUI-050]`'s `ingest_folder.py --json` already established) so the job can report the identical figures a person reading the CLI's own output already sees.

**`[SPEC-DF-114]` Measured live against the real appliance: a full pull costs over an hour, not a convenience worth reaching for casually.** vainopi's own WiFi sustains roughly 270 KB/s; a full `scp` of its ~1.16 GB database — required because `[SPEC-DF-108]` already established vainopi has no Python to run `export_flags.py` *there* — takes over sixty minutes before either job can even begin its own work. Confirmed by running the pull job live against a scratch copy of the desktop's own library and watching the transfer in progress, not estimated from the file size alone. This is not a defect in the GUI above; it is `[SPEC-DF-108]`'s own cost, now measured rather than assumed, and it is `remote-push`'s cost too — the `scp` in `[SPEC-DF-111]`'s own pipeline is the identical full-copy fetch, needed there to give `apply_changes.py`'s three-way merge something current to compare against.

**`[SPEC-DF-115]` The write to vainopi was never the expensive part, and was never a full replication — the read was, and only because a three-way merge needs the remote's *current* value to do its one real job.** `apply_changes.py`'s `classify()` (§9) exists specifically to tell apart "nothing changed there since my baseline" from "it already landed" from "vainopi diverged independently since I started" — the third case is not hypothetical: `listener_flags` genuinely changes on vainopi's own play-history page with no involvement from Sampo at all, and a second desktop syncing the same appliance would make review-table divergence possible too. A push with no remote read at all would restore this exact hazard `[SPEC-DF-105..106]` `apply_changes.py` exists to prevent — "no full database replication" and "keep the conflict safety net" are only in tension because getting the safety net's raw material has, until now, meant a full copy.

**`[SPEC-DF-116]` Built 2026-08-29, per [IMPL008](../IMPL008-targeted-remote-reads.md): targeted remote reads, moved to when an item is opened rather than when a push is sent.** vainopi already carries the `sqlite3` CLI for its own maintenance `[SPEC-DF-108]`; the same anchors (`audio_md5`, `recording_mbid`) `apply_changes.py` already resolves locally are resolved *remotely* with one small `ssh <remote-host> sqlite3 -json <remote-db> "SELECT …"` (`tools/remote_peek.py`) — a handful of bytes, not a database. The hook point is Sampo's own `/profile/:id` page, **before** the handoff to Vaino's own id-review/boundary editor `[IMPL-SUI-090]` (editing itself lives in Vaino, not Sampo — `console.py`'s `profile()` route is, and stays, read-only): opening an item fetches the remote's current value for the id and boundary identities this page can hand off, and if either differs from what this library shows, offers it as the new starting point before editing begins, rather than only at push time. Accepting it is a small, targeted local write (`tools/accept_remote_basis.py`) — the one deliberate exception to "the console never writes the library" `[IMPL-SUI-055]`, and it keeps that discipline's own shape: not `console.py`'s HTTP handler touching SQLite directly, but a dedicated subprocess tool doing exactly that one row's update, run through the job model like every other write in this console (`jobs.py`'s `accept-remote` kind).

**`[SPEC-DF-117]` This does not remove `remote-push`'s own full-copy safety net — it makes firing it, and hitting a conflict when it does, rare rather than routine.** An edit whose baseline was refreshed from vainopi immediately before editing began already matches (or was deliberately chosen to supersede) vainopi's own current value by the time a push happens, so `classify()` lands on fast-forward almost every time — proven end to end, not just argued, by `tools/test_accept_remote_basis.py`. The rare remaining case — something changed on vainopi *between* opening the item and pushing — is exactly what `remote-push`'s own read still exists to catch; that leg still costs the full `scp` `[SPEC-DF-114]` measured, since converting it to a targeted read of its own is not part of what `[SPEC-DF-116]` built.

**`[SPEC-DF-118]` Asked directly, decided plainly: vainopi being unreachable when an item is opened degrades to a visible warning, never a block.** Household WiFi to a Pi Zero 2W has already proven unreliable across this project's own Sonos investigation — a check that could not run must not stop someone from editing. Opening an item with no answer from vainopi shows *"could not reach vainopi — editing against the local baseline only"* and proceeds; whatever divergence that missed is exactly what the push-time check (`[SPEC-DF-117]`) still stands ready to catch before anything is actually written to the appliance.

**`[SPEC-DF-119]` Built 2026-08-29: `remote-pull` itself no longer costs the full copy either — `listener_flags` gets the identical targeted-read treatment `[SPEC-DF-116]` gave a single review anchor, applied in bulk.** Nothing about `export_flags.py`'s own join (a passage-kind flag's `passage_id` resolved out to its portable `(audio_md5, kind, start_ms, end_ms)` anchor) needs a local copy to run — it needs Python, which is exactly what `[SPEC-DF-108]` says vainopi lacks, not a database. `tools/remote_flags.py` runs that same join as one `SELECT` over one `ssh ... sqlite3 -json ...` round trip (`remote_peek.py`'s `run_remote_sql()`, reused rather than duplicated), and writes the identical `flags.json` shape `export_flags.py` always has — `import_flags.py` runs unchanged either way, and `export_flags.py` itself stays as the documented by-hand fallback if `ssh` access to run arbitrary `sqlite3` is ever unavailable. `remote-pull` drops its `scp`/`export` stages for one `fetch-flags` stage; proven against a real fixture and a faked (but fully wired) `ssh` round trip by `tools/test_remote_flags.py` and `tools/test_jobs_remote_pull.py`, not assumed from `[SPEC-DF-116]`'s own proof alone. `listener_flags` is small on any real appliance — tens of rows, not gigabytes — so what was over an hour `[SPEC-DF-114]` measured is now one round trip on the same order as `[SPEC-DF-116]`'s own single-anchor check. `remote-push`'s own full-copy `scp` `[SPEC-DF-117]` left standing is not touched by this — its read compares an entire exported change set, not one small table, and converting it to a batch of targeted reads (one `remote_peek.py` call per exported change, in principle) remains future work, not built here.

**`[SPEC-DF-120]` Built 2026-08-31: `remote-push` itself no longer costs the full copy either.** Asked directly: pushing four or five edited passages still cost the same ~1.16 GB / over-an-hour `scp` `[SPEC-DF-114]` measured, unconditionally, every time — `[SPEC-DF-116]`'s edit-open-time check makes hitting an actual *conflict* rare, but the read itself still ran at full cost regardless of whether one existed. `tools/remote_snapshot.py` is `[SPEC-DF-119]`'s own answer applied to the leg it explicitly left standing: one `remote_peek.py`-style `ssh ... sqlite3 -json` round trip per exported change (two for a boundary edit whose anchor span has already moved once, mirroring `resolve_boundary_passage()`'s own local fallback), reconstructed into a disposable SQLite file just complete enough for `apply_changes.py`'s existing merge logic to run against, **unmodified in behaviour**: `apply_changes.py` itself gained module-level `ID_REVIEWS_TABLE`/`BOUNDARY_REVIEWS_TABLE`/`ARTIST_REVIEWS_TABLE`/`REVIEW_TABLE_MIGRATIONS` constants so `remote_snapshot.py` could reuse its exact schema rather than duplicate it, but `ensure_review_tables()`'s own logic is untouched — the snapshot is a drop-in replacement for what used to be a full `scp` copy, nothing more, so the three-way merge's own correctness guarantee (`--emit-sql`'s literal trace of code that actually ran) is unchanged.

One correctness gap needed closing beyond a plain per-anchor read: `apply_id_review`'s own recording-creation branch is a plain, non-`OR IGNORE` `INSERT INTO recordings`, which collides if the target mbid already exists on the remote under some *other* passage entirely — invisible to a snapshot built only from the one anchor being pushed. `remote_snapshot.py` fetches that existence check too, in the same round trip, closing the one way a naive per-anchor reconstruction could turn a clean fast-forward into a failed statement against the real remote.

A second, deeper gap surfaced only once `tools/test_e2e_push_pipeline.py` exercised the real chain end to end — draft, saved exactly as Vaino's own editor leaves it, through `apply_boundary_reviews.py`, `export_changes.py`, `remote_snapshot.py`, and `apply_changes.py`, landing on a genuinely separate "remote" database, no synthetic `changes.json` typed by hand. The first version of `remote_snapshot.py` pre-ran `apply_changes.ensure_review_tables()` on every snapshot to give a history row somewhere safe to land; against a real remote that had *never* had one of the three review tables at all, that "used up" the very `ALTER TABLE` statements `apply_changes.py`'s own later run needs to discover fresh and capture into the patch — the review table would exist on the snapshot with every column already present, so the genuinely-missing columns on the real remote would never be added, and the first real `INSERT` referencing one would fail outright. Fixed by having `remote_snapshot.py` ask the remote's *own* schema, per table and per migrated column (`PRAGMA table_info`, one round trip per existing table), and pre-add to the snapshot only the migrations the remote genuinely already has — a table entirely missing stays bare, a fully-migrated remote's snapshot ends up fully migrated too, and anything in between (a real installation that predates `[SPEC-SUI-226]`'s fade columns, say) is reproduced exactly, not rounded to either extreme. `tools/test_remote_snapshot.py` proves the property that actually matters end to end: for the same `changes.json`, a snapshot's `apply_changes.py --emit-sql` output is byte-identical to a full copy's, across fast-forward, conflict (including its own applied-review history, which never reaches the write patch and so needed its own check), missing, the target-already-known-elsewhere hazard above, the target-span fallback, a remote that has never run `tools/add_fade_columns.py` at all, and now a remote whose review table exists but predates `[SPEC-DF-104]`'s `origin` column specifically. `tools/test_jobs_remote_push.py` proves the job wiring: `export -> snapshot -> compare -> send -> apply-remote`, no `fetch`/`scp` stage anywhere, and a `snapshot` failure stops the job before `compare` ever runs. The full-copy recipe `[SPEC-DF-111]` documents stays as the by-hand fallback if targeted `sqlite3 -json` access to the remote is ever unavailable — the identical relationship `[SPEC-DF-119]` already left `export_flags.py` in for `remote-pull`.

**`[SPEC-DF-121]` A real, previously-uncaught bug in `[SPEC-DF-111]`'s own apply-remote step: a bare `systemctl` fails outright as the unprivileged deploy user.** Found live 2026-08-31, the first time this exact stage ever ran against a real vainopi rather than a faked `_spawn` — `systemctl stop vaino` over `ssh` as `pi` answers `Failed to stop vaino.service: Interactive authentication required`, because `pi ALL=(ALL) NOPASSWD: ALL` (`[PI5-PRIV-010]`) grants root through `sudo`, not free rein over `systemctl` without it. `VainoPi/deploy-player.sh` already knew this — its own `systemctl` calls were always `sudo systemctl` — but `jobs.py`'s `_remote_push` never matched it, and no test caught the gap: every existing test faked the `apply-remote` stage's `_spawn` call wholesale, checking that it *ran*, never what command it actually built. Fixed by prefixing both calls with `sudo`; `tools/test_jobs_remote_push.py` now captures the real argv for that stage and asserts `sudo` is in it, closing the coverage hole that let this ship unnoticed.

**`[SPEC-DF-122]` Built 2026-08-31: `tools/push_file_tags.py`, a small standalone sibling for a table §9's own pipeline was never scoped to carry.** `[REQ-LIB-146]` fixed `ingest_folder.py`'s tag-reading gap and repaired the *local* library, but `export_changes.py`/`apply_changes.py` only ever move the three review-draft tables — raw `file_tags` was out of scope by design, and vainopi's own mirror kept the identical gap after the local fix landed, found live checking the exact 28 files `[REQ-LIB-146]` had just repaired. It matters there too: `player/src/db/library.rs`'s (`db.rs` at the time, split 2026-09-01) `ARTIST_EXPR`/`ALBUM_EXPR`/`TITLE_EXPR` (`[REQ-VIS-250]`) fall back to `file_tags` for any passage with no linked MusicBrainz recording, so the gap was visibly blank artist/album on vainopi's own browse page, not only a Sampo-side matching inconvenience.

Deliberately not a widened `apply_changes.py`: raw `file_tags` has no baseline to three-way-merge against and cannot meaningfully conflict the way a human's own review edit can — the same audio hashes to the same tags everywhere, so an empty remote row is only ever a gap to fill, never a difference to arbitrate. The remote drives what gets checked, not the local library: one filtered `SELECT` asks the remote directly for the audio it considers entirely untagged (every field NULL, `[REQ-LIB-146]`'s own defect shape), answered only as large as the remote's real gap — 28 rows against this project's own library, never the size of the whole `files` table `[SPEC-DF-114]`'s own lesson already argues against sweeping. Only those named ids are then looked up locally, and only the ones this library can actually offer something for are built into a patch and pushed, matched by `audio_md5` (never `file_id`, which two installations have no reason to agree on `[SPEC-DF-040]`) via `WHERE file_id = (SELECT file_id FROM files WHERE audio_md5=?)`. `--target` defaults to the same `remote_config.sync_remote` the console's own "Sync with a remote" page already remembers, so a builder who has that set needs nothing beyond `python tools/push_file_tags.py <db> --commit`. The literal patch SQL is captured via `set_trace_callback` against a throwaway connection — `[SPEC-DF-111]`'s own `--emit-sql` pattern, reused rather than hand-rolling a second escaper — and applied through the identical `sudo systemctl stop && sqlite3 ... && sudo systemctl start` recipe `[SPEC-DF-121]` just corrected (`--no-sudo` for a remote that needs none). Verified live: pushed the same 28 files by hand as a one-off patch before this tool existed, then confirmed `tools/push_file_tags.py`'s own logic reproduces that exact set. `tools/test_push_file_tags.py` covers the gap query's shape, the local-side filter, patch quoting (SQLite's own, not hand-rolled), the dry-run/`--commit`/`--no-sudo` wiring, and the sidecar-config lookup, all against a faked `ssh` round trip.

**`[SPEC-DF-123]` Built 2026-09-01: unflag from Sampo's own profile page `[REQ-VIS-280]` — by asking Vaino to do it, not by writing `listener_flags` from this process.** `[REQ-LIB-190]`'s rule was never in question, only whether it forced a person over to Vaino's own play-history page for a decision Sampo's profile page is the more natural place to act on. `player/src/web/browse.rs` (`web.rs` at the time, split 2026-09-02) already exposes exactly the write needed, unconditionally: `POST /history/flag/:kind/:id?flagged=` (the play-history checkbox's own route). `console.py`'s `_vaino_set_flag()` calls it on the co-resident Vaino over plain HTTP; `_remote_set_flag()` calls the identical route on vainopi's own already-running Vaino over one `ssh ... curl` round trip — never a database write from this process either way, and never a service interruption, since nothing here writes to either database directly for a running player to race against.

A passage-keyed subject (`("passage", pid)`) is only meaningful locally — `pid` is not portable `[SPEC-DF-103]` — so `remote_peek.py` gained a `passage_flag` kind that resolves the remote's own local passage_id from the portable anchor in the same round trip that checks whether it is flagged, the shape `[SPEC-DF-116]` already established for id/boundary checks. The display (two dots — shown/local, and vainopi, agreeing in green or diverging in yellow — `[SPEC-DF-115]`'s point that vainopi's own flags can change with no involvement from Sampo at all) needed only that. Clearing needed one thing more, found live the first time this ran against a real divergence rather than a fixture: an id correction accepted locally (a real MusicBrainz recording, via `[SPEC-SUI-215]`'s own release-accept flow) but not yet pushed left vainopi still linked to the *old* `local:audio:` placeholder — resolving subjects only from this library's own current recording link cleared nothing where the flag actually was, because a `DELETE` matching zero rows still reports success. `passage_flag` now returns the remote's own currently-linked recording(s) too (`json_group_array`, one more column in the same round trip), and `unflag_everywhere()` clears the *union* of this library's link and the remote's own — the identical reasoning `[SPEC-DF-112]`'s `clear_flags_for()` already applies to an `id_review`'s target and baseline, generalized to "ask what the far side currently thinks too." `tools/test_console_unflag.py` reproduces this exact divergence as a fixture, not only the live incident that found it.
